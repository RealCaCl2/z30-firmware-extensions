# 全尺寸 DX 横向裁切实验（v9 判定实验）

后续已从 v10 实机日志定位到菜单版本遗漏的另一张裁边表，v11 已补齐并完成原厂函数重放，仍待实拍。见[最新诊断结论](aspect-diagnostic.md)。本页的两个 v9 产物不作为当前测试候选。

日期：2026-10-17。此为两个独立的原厂 DX 表实验，不是已修复的多画幅菜单版本。v8 的 4:3、5:4 仍有实机横向压缩，当前不宣布修复。

## 最新实机结果：4:3 判定失败

用户测试 4:3 实验后反馈取景比例异常、成片画面内容仍与 DX 相同，随后确认主 JPG 为 **4952×3712**。输出尺寸已变化，不能记成“JPEG 仍为原厂 DX 尺寸”；正确记录是“输出尺寸生效，但未观察到预期的左右内容裁切”。结合反馈，这与完整 DX 内容被横向缩入较窄输出一致；本轮没有新原始 JPG 可供独立像素配准。

该结果否定了本实验的裁切效果，不证明 DX 架构不能实现横向裁切，也不能仅凭它断定配置函数完全不执行。5:4 独立实验尚未获得本轮测试结果。不要继续把这两个产物作为已修复版本使用。


## 改动范围

从身份校验通过的 Z30 C1.20 原版 EG 出发，仅修改 DX 的三档输出宽高表 `0x115A4DA8 + size*4` 和横向 trim 表 `0x11571E18 + size*4`，再重算模块 CRC。无注入代码、无扩展菜单，不包含 full 的其他功能。DX 父区域保持 5568×3712、原点保持 (16,8)。

| 独立版本 | L | M | S | 全尺寸左右各裁 |
|---|---|---|---|---|
| 4:3 | 4952×3712 | 3712×2784 | 2472×1856 | 308 |
| 5:4 | 4640×3712 | 3480×2784 | 2320×1856 | 464 |

4:3 的 L/S 为现有八像素量化策略，比例有微小误差。M/S 输出表同步修改以免留下明显不一致，但首轮实机判据只针对 JPEG L。

这不是 v5 的 parent/origin 重写，也不是 v8 的 area-2 影子表：它直接测试原生 DX 分支是否消费 horizontal trim。尚未定位实际 ISP 消费者，因此不能保证它会真正裁切像素。

## 本地验证

构建工具执行原厂 `0x1014237A` 配置函数及输出缓冲区、描述辅助函数等，每版九例（area 0/2/4 × L/M/S）。断言 DX 的 parent、origin、trim、trimmed、output 与目标一致，输出缓冲区宽高一致；非 DX 六例完整测量结果与原版相同。实际改动只能出现在记录的表字节和末尾 CRC，文件长度不变，CRC 残差为零。

这些检查不包含传感器、ISP 像素、JPEG 编码或机身回放，`camera_verified` 保持 false。内嵌预览未改，不能用普通机内回放判断本实验的主图裁切。

```powershell
python tools/build_dx_aspect_trials.py --deps build/verify-deps --output-dir output/my-dx-aspect-experiment
```

输出目录必须不存在。每版包含 `EG209020.BIN`、改动及验证报告和 SHA-256。产物是项目既有工作流中的 EG 模块，**不是完整 Nikon 外层升级容器**；文件名和模块 CRC 不证明它可通过官方更新菜单安装。本工具不刷写相机，也不写物理卡。

当前本地输出：`output/dx-aspect-trim-v9-experiment/4-3/` 与 `5-4/`。

- 4:3 SHA-256：`b48bc9fa475b2da5fe420cdaa2d07bfbc86ece1bc78ad8ea73a6267744f679d4`
- 5:4 SHA-256：`275f444a3a109e30333ded627fd9a585538156d68f1bf470c2839f2fa41979a2`

## 实拍判据

1. 使用已经确认适用的 EG 加载流程，分别测试两版；不可把裸 EG 当外层升级文件直接提交给官方更新菜单。
2. 原厂图像区域选 DX，JPEG 选 L。固定相机、焦距及拍摄位置；选一个中央圆形物体，左右边缘均放可辨识标记。保留同位置原版 DX 对照。
3. 在电脑打开主 JPG，核对尺寸及边缘内容。4:3 应左右各去掉约 308 原图像素，5:4 各约 464；中央物体应维持对照图的横纵比例和像素尺度。
4. 如果只是整幅画面变窄、边缘标记仍全部存在，即实验失败；输出尺寸正确不能算成功。停止把 trim 配置作为已验证裁切入口，继续追踪实际像素处理路径。

仅实拍确认后才考虑重新集成菜单、预览和参考框。原始照片、EXIF 与调试日志保留在本地，不进入版本库。当前状态与其余限制见[多画幅说明](aspect-profiles.md)。

## 失败后续：下游处理链验证与 v10 诊断

已从只读静态线索推进到原厂下游函数执行，工具为 `tools/verify_aspect_processing_route.py`。测试采用原版、4:3 DX 实验、5:4 DX 实验，分别覆盖 area 0/2/4 × L/M/S，共 27 例。

| 阶段 | 原厂入口 | 已核对行为 |
|---|---|---|
| 配置构造 | `0x1014237A` | 生成 parent、trim、trimmed 和 output |
| 配置消费 | `0x100A4E20` | 从拍摄上下文 `+0x30C` 取配置，生成 72 字节请求 |
| 请求入口 | `0x100EF7B8` | 按输入类型选择请求准备路径；本次验证在入口截获 |
| 普通上下文准备 | `0x100EF6DE` | 把请求裁边复制到处理对象 `+0x4C..+0x58` |
| 参数转换 | `0x102507CA` | 把四边裁边复制到参数 `+0x3B0..+0x3BC` |
| mode 2 计算 | `0x1024C084` | 从源宽高减去四边，生成有效宽高与 Q16 缩放参数 |
| 模型停止处 | `0x1024B7A8` | 图块打包器被替代，不计入已验证阶段 |

构造输入下，4:3 的请求与参数均保留 `(308,308,0,0)`，5:4 保留 `(464,464,0,0)`。L 档有效输入宽高等于目标输出，Q16 横纵比例均为 65536（1:1）。原生 1:1 的 `(928,928,0,0)` 也走到同样的计算阶段。

因此“所有实机处理路径都不读 trim”的说法没有证据；现在至少已经执行到一个会消费 trim 的下游分支。还不能据此认定实机拍摄选择了这个分支，或硬件执行了生成的参数。

本地报告：`build/research/aspect-dx-feasibility/processing-route.json`。上下文为合成；准备调用 `0x100A11CA` 被替代，主请求在入口截获后独立执行准备/转换，仅执行 mode 2，未生成图块命令或图像像素。

为核对实机，生成 `output/full-aspect-processing-trace-v10/EG209020.BIN`，SHA-256 为 `13e428c75f7a6ce819358a87577c9b41dd470fca422994eedef580d52eb8a225`。这是 full + aspect-profiles 的**诊断版**，保持当前未修复的成像实现，不是新的裁切修复；也不是外层 Nikon 升级容器。操作及格式见[诊断说明](aspect-diagnostic.md)。
