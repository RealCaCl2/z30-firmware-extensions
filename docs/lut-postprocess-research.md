# 拍摄后在机内套用 3D LUT：Z30 C1.20 研究

2026-10-29。目标是回放选择已有 JPEG，读取 SD 卡上的 `.cube`，处理后另存 JPEG。第一阶段限定本机拍摄的 sRGB JPEG、单张操作、原图保留；这是一项研究范围约定，尚未实现该机内功能。

**原厂已经实现解码、修饰、编码和另存副本；研究目标是恢复并复用这些接口，在处理环节加入 LUT。** 第一轮找到服务和效果表，第二轮连接请求构造与处理入口，第三轮恢复编解码参数和部分缓冲合同，第四轮连接保存阶段内的效果输出、主图编码及清理，并将 JPEG 组装描述接到原厂写入器边界。各轮结果按时间保留，后文更新前文的研究边界。尚未在相机上运行 LUT。本轮未访问相机，未生成固件，未改动 `full`、菜单、模块 ABI 或现有功能。

## 原厂已有的产品能力

尼康 Z30 [修饰菜单说明](https://onlinemanual.nikonimglib.com/z30/en/09-07.html)明确说明：修饰处理已有照片，结果保存为与原图分开的新文件；可以在回放按 i，选择修饰当前照片。菜单实际包含 D-Lighting、单色、尺寸调整等项目。这证明产品本身有照片编辑和保存副本能力，**不等于其内部接口已经恢复**。

[尺寸调整说明](https://onlinemanual.nikonimglib.com/z30/en/09-07-03.html)也描述了生成和保存小尺寸副本。不过，我们的最终目标是全分辨率照片，不能用小图编辑成功代替全尺寸验收。官方同时指出，其他设备生成或电脑修改过的图片可能无法在机内修饰；早期输入限定本机原生照片。

之前搜索到的 `QUICK RETOUCH` 等固件字符串位于修饰信息名称表附近。官方当前菜单没有该项，不能将历史名称、通用 EXIF 标签表或某段字符串认定为可用菜单入口。

## 本轮恢复的原厂结构

固件源为身份校验通过的原厂 C1.20 EG，SHA-256 为 `8a99ced2d8220729ba067587b0624bf30c81757abc5d728768134b1c7fd457fa`。地址只适用于这个版本。

### 回放服务与调用点

| 观察点 | 本轮证据 | 尚不能断言的内容 |
| --- | --- | --- |
| `PlaybackProcessS`，ROM `0x12069F58`，运行时 `0xC18E82C4` | 初始化数据中的服务名称，前一字为 `0x04160000` | 不是函数地址，也没有恢复请求参数全部语义 |
| `0x10348130` | 函数读取消息 `+0x10`，部分分支更新状态，再把消息交给 `0x1021157C` | 这是提交路径的静态证据，不是同步解码函数；没有恢复完成/等待合同 |
| `0x10424452` | 可解码的调用窗口提交消息；附近消息码为 `0x0416000C` | 尚未把该码对应到某一个具体修饰菜单操作 |
| `0x10347B04` | 读取消息 `+0x10`，范围判断后通过 TBB 分派；分支中可见到 `0x1034364E` 等处理入口 | 尚未执行完整消息状态机或证明完整 JPEG 处理路径 |
| `ImageFormatServi`，ROM `0x1206A018` | 格式服务名称及其他静态引用 | 名称不等于 JPEG 解码器接口 |

`0x10348130` 的半字 BL 模式在扫描范围内有 61 个候选。模式扫描包含数据和可能错误的指令边界，不能把数量称作 61 个已确认调用者。选定窗口的指令解码也不等于从菜单可达。

### 图像效果函数表

表位于运行时 `0xC181099C`。本轮恢复 20 个 Thumb getter，每个均为 `LDR r0,[pc,#imm]; BX lr`，返回各自的初始化描述结构。

描述结构中可见以下使用方式：

| 字段或入口 | 实际执行/指令证据 |
| --- | --- |
| 描述结构 `+0x14` | 第二轮确认由真正任务入口 `0x100CC910` 调用的效果处理函数，详见后文 |
| 描述结构 `+0x18` | `0x100CCAB0(index, argument)` 先判断 `index < 20`，取 getter，再判断此字段非空，调用时 `r0=argument` |
| 描述结构 `+0x1C` | `0x100CCAD4(index, argument)` 选取并调用另一函数指针；本入口未见同样的索引上限判断 |
| 描述结构 `+0x20` | 各项为 `0x43100002` 至 `0x43100015` 的标识值；不把其解释为像素或内存地址 |
| `0x100CCA42` | 静态代码分配 `0x1C` 字节消息并入队；参数首字非零和为零走不同路径。创建/队列/等待未执行验证 |
| `0x100CCA12` | 在人工消息中，参数首字非零时，将描述结构标识值放入 `r0`，参数指针放入 `r1`，调用参数首字中的函数指针，然后回收消息；零回调分支调用事件服务后回收消息 |

`+0x18` 非空的索引为 **4、5、9、10、17**。这里的“可选回调”和“查询回调”是工具里的研究名称，实际操作语义还未绑定。20 个内部效果索引不能按 EXIF 修饰编号、菜单顺序或 Picture Control 编号直接映射。

例如索引 4 的 getter 为 `0x10262D78`，描述结构为 `0xC1810B70`，`+0x18` 指向 `0x10264F8F`（Thumb），`+0x1C` 指向 `0x1026502D`。这证明存在实际代码和分派合同，尚未证明这些函数对哪种图像或哪个效果工作。

此框架值得追踪为处理任务候选，但**尚不能直接插入 LUT 回调**：任务上下文、堆栈、参数生命周期、取消与互斥、缓存一致性，以及和回放修饰的关系都未确认。不能通过增加索引 20 或覆盖原厂表项来试机。

### 像素和保存：当前边界

- 原厂图像调试区存在 `YCbCrFormat`、`LineBytesY`、`LineBytesC`、`AddressY` 和 `AddressC`，位于 `0x100BA470` 等地址。这提示原厂有 Y/C 平面和行步长概念，**没有证明本次回放修饰解码缓冲的格式**。必须确定色度采样、平面排列、范围、矩阵、位深和有效窗口后，才可做颜色转换。
- `IMPJPGCO` 和 `IMPJPGEN` 名称存在于初始化数据；`JPEG_CODEC` 和 `JPEG_ENC` 也出现在中断名称区域。名称不是可调用解码/编码入口，未恢复提交结构、完成中断或资源所有权。
- 既有研究中的 `0x1033DF28` 分派到照片保存代码；`0x102B6EC0` 已有低层写入器的合成夹具。它们面向原厂照片描述对象，不能直接塞入任意 LUT 处理后的 JPEG 字节。既有保存研究边界见 [JPG 原生缓存原型](jpg-precapture-core.md)。
- DCF 编号、新文件创建、EXIF、缩略图、回放登记及失败回收合同仍未为本功能恢复。本轮没有执行这些服务。


产物为 `build/research/lut-postprocess/inventory.json`、`windows.txt` 和 `dispatch.json`，都属于本地生成诊断，不是固件或发布附件。

第一轮 **83 次原厂入口调用通过**：20 次 getter、20 次可选选择、20 次查询选择、20 次非零回调完成消息、1 次零回调完成消息，以及 2 次可选选择的越界索引拒绝。公共执行夹具检查保存寄存器和栈平衡。回调返回值被替换为固定 `0x55`，用于检查传递和返回，不代表任何原厂成功状态。

这些检查证明局部分派行为，**未执行效果算法，也没有输入图像**。不能表述为 LUT 已运行、JPEG 编解码已通过、完整任务已工作、机身处理时间已测量或保存安全已验证。

## 处理方案与内存预算

优先方案是复用原厂“打开照片、解码、编码、另存”的生命周期，在中间明确归调用者所有的像素缓冲上运行软件 3D LUT。拍后处理不必先找到硬件 3D LUT 单元，但是否能高效访问完整图像仍需证明。

下表仅为数学预算，不是机身可分配空间或性能实测：

| 数据 | 字节数 | 说明 |
| --- | --- | --- |
| `5568×3712` RGB888 一帧 | 62,005,248 | 约 59.1 MiB，编码输出和其他工作区另计 |
| `17³` LUT，RGB 每通道 16 位 | 29,478 | 不含解析器和索引结构 |
| `33³` LUT，RGB 每通道 16 位 | 215,622 | 约 211 KiB |
| `5568×64` RGB888 条带 | 1,069,056 | 约 1.02 MiB；不代表原厂 codec 能按条带输出/输入 |

若编码器要求保留整个 YCbCr 帧，条带 LUT 只能减少额外 RGB 工作区，不能消除原厂全帧占用。双 RGB 缓冲还会使该项翻倍，不能默认可用。

第一版颜色合同建议明确为：8 位 sRGB 编码 RGB 输入、`.cube` 三维表、固定三线性插值、明确范围和裁剪策略。确认文件的点序和 `DOMAIN_MIN/MAX`；不把 N-Log、其他 Log 或 Adobe RGB LUT 直接当作 sRGB LUT。以上是拟定合同，尚未实现解析器或 LUT 内核。

## 下一轮决定性关口

1. 从一项官方实际存在的 JPEG 修饰功能（优先单色或 D-Lighting）追到 `0x10348130` 的消息码、处理分支及完成回调。预览和最终保存必须分别追踪，避免误把显示小图当主图。
2. 恢复解码器输入、主图尺寸、输出平面/步长、所有权和释放；找到可在 CPU 上修改且不会被并发覆盖的时点。先确认一个小区域，再确认全尺寸。
3. 恢复处理后编码和原厂修饰副本提交合同。先做无 LUT 的解码/重编码另存，并检查原图哈希、新 JPEG 全尺寸解码、EXIF/方向、缩略图和重启后回放。JPEG 重编码通常有损，不能把输出文件逐字节相同作为要求。
4. 上述链路成立后，再做单位 LUT、交换色通道 LUT 和色块/灰阶图验证，并测量时间与峰值内存；随后加入 `.cube` 选择和正常用户界面。

若原厂 codec 不支持条带或难以取得处理缓冲，可评估自带软件 JPEG codec 的替代路径；这会增加代码体积、内存、速度和元数据整合工作，目前未选型或引入依赖。上述任何路线都不能由当前局部分派检查直接宣布可刷写。

## 第二轮：沿原厂修饰路径追到处理入口

本轮重点从“原厂已经有完整流程”的事实出发，追踪如何替换其中的效果处理。新增 `tools/trace_lut_retouch.py`，结果保存于 `build/research/lut-postprocess/retouch-trace.json`。

### 请求到效果的连接

恢复了两层不同的编号体系，不能混用：

- 修饰操作码存于请求 `+9`，例如 5、6、7。
- 图像效果服务的内部处理索引存于后端对象 `+8`，这三个操作都映射为 **6**，另有模式字段区分三个变体。

操作 5/6/7 的“三种变体 + 各自强度 + 固定变换表”的行为与单色/棕褐/青色系列相符；操作 1 的三档处理与 D-Lighting 相符。这是函数行为支持的**名称推断**，还没有从实际菜单事件或机身追踪日志绑定英文/中文名称。下面用操作码给出可复核结果，不把名称猜测当入口地址的证明。

| 层级 | 地址 | 恢复的行为 |
| --- | --- | --- |
| 显示侧构造器 | `0x104235A2`，上层跳板 `0x10387418` | 第一选项 0/1/2 转成请求操作 5/6/7；第二选项归一到 0/1/2；复制显示图像的地址与几何 |
| 另存侧构造器 | `0x10424672`，上层跳板 `0x103876D6` | 相同操作/选项映射，返回新照片句柄及错误标志；不从显示图像复制完整主图 |
| 服务提交 | `0x10348130` | 两个上述构造器都提交 `0x04160004`；请求 `+8` 另有上下文阶段字段，不能只靠消息码区分预览/保存 |
| 服务分派 | `0x10347B04` | 原厂 TBB 将 `0x04160004` 路由至 `0x10344828`，完成时把消息码和用户上下文传给回调 |
| 处理组织 | `0x10344828` | 静态保存分支在 `0x10345124` 调用 `0x1038F64A`，成功后取得结果句柄并调用 `0x103415B4`；尚未完整执行此函数 |
| 效果设置 | `0x1038F64A`，表 `0x115CD6CC` | 操作 5/6/7 选择参数构造器 `0x1038F91E`，构造内部索引 6 和模式 0/1/2；操作 1 选择索引 0 |
| 输出绑定 | `0x100A535A` | 为索引 0、6 把输出描述结构绑定到参数 `+0x10`，复制输入的格式/几何，保留已分配的输出平面地址 |
| 效果提交 | `0x100A554E` / `0x100A5726` | 调用 `0x100CCA42`。这些点是静态调用和局部参数合同证据，未执行完整异步后端 |
| 真正执行任务 | **`0x100CC910`** | 按消息 `+0x10` 取效果 getter，调用描述结构 `+0x14` 的处理函数；参数为消息 `+0x14` 指向的对象 |
| 索引 6 处理函数 | **`0x1025FB8E`** | 验证参数、构造处理状态、提交硬件并等待；结果写入参数 `+0x14` |
| 完成处理 | `0x100CCA12` | 前一轮称作 worker 的函数实际是完成路径；真正处理入口为 `0x100CC910`。它传递完成标识、调用调用者回调或发事件，再回收消息 |

另外，`0x0416000C` 实际经 TBB 的二次短跳转进入 `0x10342FE4`，**不是** `0x103453A6`。后者对应 `0x0416001B`。新增工具实际执行了 04 和 0C 的分派，处理函数被替换为边界桩，完成回调参数也做了核对。不能根据线性反汇编中“附近的 BL”推断 TBB 的目标。

### 恢复的图像描述结构

索引 6 的输入位于参数 `+4` 指向的描述结构，输出位于参数 `+0x10`。两者至少需要下列字段：

| 偏移 | 长度 | 指令支持的含义 |
| --- | --- | --- |
| `+0` | 1 | 格式码；索引 6 的验证器接受 1、2 |
| `+1` | 1 | 其他标志，语义未绑定；输出绑定器会保留输入取值 |
| `+2` | 2 | 第一平面的行步长 |
| `+4` | 2 | 第二平面的行步长 |
| `+6/+8` | 各 2 | 缓冲/全幅几何，具体与有效窗口的区分待继续核对 |
| `+0xA/+0xC` | 各 2 | 本次处理的宽和高；验证器要求输入输出一致 |
| `+0xE/+0x10` | 各 2 | 横向、纵向起点偏移 |
| `+0x14` | 4 | 第一平面的基址 |
| `+0x18` | 4 | 第二平面的基址 |

地址计算不是紧密连续 RGB。原厂 `0x1025FBCA` 的第二平面寻址，在格式 1 下为 `base + 2*(x>>1) + stride*y`，格式 2 下为 `base + 2*(x>>1) + stride*(y>>1)`。这符合水平色度减半的交错色度寻址，两个格式分别具有 4:2:2 / 4:2:0 的寻址特征；**Cb/Cr 顺序、范围、转换矩阵、实际机身缓存一致性仍未确认**。

在 `0x1025F990` 可以看到，第一平面的有效起点为 `Y_base + x + Y_stride*y`，第二平面使用上述助手。验证器还限制行步长/起点对齐、模式取值、工作结构非空和输入输出宽高一致。

### 原厂效果如何执行

索引 6 会在 `0x1025F990` 设置变换系数和多张固定表，随后 `0x1025F88E` 构造图像处理描述，最终在 `0x1020182C` 前准备好提交对象。构造状态中可见三段长度为 `0x800` 的表以及系数表地址；这**不构成任意 `.cube` 三维查表支持的证据**。

本轮用 32×16、步长 64 的人工图像描述结构，分别执行两个格式、三个模式，一共 6 个案例。原厂参数验证和描述构造确实执行，到 `0x1020182C` 时主动停止。期间仅替换事件清除服务 `0x10199E0A`，未访问硬件；输入输出像素区保持哨兵字节不变。这证明的是进入硬件前的地址和配置传递，**没有产生单色或 LUT 效果图像**。

### 对 LUT 接入方案的直接影响

现在优先候选是 **`0x100CC910` 中处理函数调用之前**，或由该处选择的特定处理入口。该位置已经有输入和输出描述结构，并且处理结束后能自然接回原厂完成通知；无需重写文件选择、照片编码和另存界面。

新增验证还执行了真正任务入口和原厂完成处理：把索引 0、6 的效果函数替换为明确的测试桩，写入人工成功状态，再分别走“调用者回调”和“事件通知”两条路径，均能继续到消息回收。这里替换的是处理算法，**没有证明软件 LUT 的性能或真实任务时序**。

初步实现方向应为：只对具有独立 LUT 请求标记的这一次作业选择软件处理，写入原厂已绑定的输出缓冲，按该效果的完成合同返回。正常原厂作业继续调用原来的算法。不能简单在单色完成后追加 LUT，否则颜色已经丢失；也不能仅调用完成回调而不生成有效输出。

还有三个需要用实际缓冲与状态确认的关键问题：

1. 原厂解码完成到上述效果入口之间，是否已经完成 DMA/缓存同步，输入缓冲能否稳定供 CPU 读取；输出缓冲在编码开始前需要怎样清理缓存。
2. 真实 JPEG 作业使用哪一个格式码、Cb/Cr 顺序、颜色矩阵与范围；软件 LUT 的 RGB 转换及色度重采样需按此实现。
3. 原厂会对主图、缩略图或预览分别启动几次处理；请求标记和 LUT 参数必须跟随作业，不能靠全局“下一张”状态推测。完整主图尺寸与保存后回放仍须独立验收。

下一步先沿这两个明确边界恢复同步和输出合同，再做一次受控、保持颜色的简单软件处理作业接入。JPEG 编解码和另存继续使用原厂现成流程。

## 第三轮：缓冲生命周期与原厂 JPEG 接口

新增 `tools/trace_lut_buffers.py`。本轮继续恢复原厂接口，不另写 JPEG codec。结论是：**图像平面到原厂编码请求、编码结果到原厂对象的接口已能分段执行；CPU LUT 所需的真实缓存交接和完整另存状态机仍未打通。**

### 解码和编码方向已区分

原厂 codec 任务入口 `0x1021934C` 根据消息码分派：

| 消息 | 原厂处理入口 | 支持方向判断的证据 |
| --- | --- | --- |
| `0x42181801` | `0x1021923E(message, 0)` | 接收宽高、Y/C 步长与地址、压缩输出区；完成后返回压缩长度。对应编码请求 |
| `0x42181802` | `0x10219634(message)` | 包装器接收压缩输入地址和目标 Y/C 平面，处理后更新图像有效宽高。对应解码请求 |
| `0x42181803` | `0x1021923E(message, 1)` | 同一编码处理体的另一模式；不能命名为 JPEG 解析器。它同时是上述任务部分失败情况下发出的回调码，必须结合请求/回调位置解释 |

解码包装器 **`0x10096F88(source, image_descriptor, optional_crop)`** 将来源 `+8` 的压缩输入指针，以及图像描述结构 `+2/+4` 的步长、`+0x14/+0x18` 的目标平面传给 `0x102194BC`。本轮实际执行该包装器，替换同步 codec 调用，分别验证格式 1/2、提交失败和 codec 状态失败。无裁切时，它从返回参数 `+0x2E/+0x30` 更新有效宽高。调用者为 `0x100A4D20` 内 `0x100A4DEA`，会依请求选择主图或不同大小的内嵌图，不能把任意一次成功解码当作主图成功。

编码包装器有两条已找到的路径：

- **`0x10390C42`**：在 `0x10348376` 内被调用，接收双平面、宽高、压缩目标区和选项；构造 `0x42181801`、回调 `0x1034001D`，等待掩码 `0x2080`，成功把 codec 参数 `+0x48` 的压缩长度写回调用参数 `+0x20`。实际执行了 32×16 和 5568×3712 的参数案例，包含等待错误分支；没有按全尺寸分配像素，也没有编码出字节。
- **`0x10096EE6` → `0x100978A4`**：直接接收前一轮恢复的图像描述结构。格式 1/2、有效宽高、两平面步长/地址进入同样的编码参数；支持同步和异步两条路径。它被 `0x100A60F2` 等主图/派生图组织函数调用。

第二条路径中，`0x100978A4` 构造的 codec 参数至少有下列合同：

| 偏移 | 字段来源与用途 |
| --- | --- |
| `+0` | 图像格式 1/2 |
| `+2/+4` | 图像描述结构 `+0xA/+0xC` 的有效宽高 |
| `+0xC/+0x10` | 图像描述结构 `+2/+4` 的 Y/C 步长 |
| `+0x14/+0x18` | 图像描述结构 `+0x14/+0x18` 的 Y/C 地址 |
| `+0x1C` | 输出对象 `+8` 的压缩目标地址 |
| `+0x20` | 调用参数 `+8` 的输出容量字段；尚未验证底层越界拒绝行为 |
| `+0x34` | 编码选项结构 |
| `+0x40` | 完成后由 `0x10096E96` 检查的状态字节；非零转成结果状态 0，零转成结果状态 1 |
| `+0x44/+0x48` | 完成后复制到结果结构的压缩地址与长度 |

`0x10096EE6` 分配 `0xE0` 字节作业。异步时消息位于作业 `+0xB8`、回调为 **`0x10096E97`**；同步时调用 `0x10219468` 后也进入同一个结果处理体。`0x10096E96` 把状态、压缩地址/长度和附加结果复制给调用者，同时更新输出对象 `+0xC` 的长度，异步时再通知，最后释放 **codec 作业结构**。这不是释放压缩像素缓冲或提交 SD 文件。

新增 8 个案例实际执行图像描述绑定、请求组织、原厂结果复制和作业释放，覆盖格式 1/2、同步/异步、人工成功/失败。压缩地址/长度由 codec 边界桩写入；异步完成在请求返回后单独驱动。**失败时原厂也会复制这些结果字段，因此必须检查状态，不能只看到长度非零就保存。**

原厂 `0x102194E4` 还可扫描 JPEG SOF 标记，提取尺寸。用主机生成的 37×19 基线与渐进 JPEG 各执行一次，尺寸均正确。这仅验证标记扫描，不证明相机支持渐进 JPEG 像素解码。

### 缓冲申请和归还

`0x10142ACA(owner, metadata)` 的通常分支从池 9 申请对象，经 `0x1014237A` 初始化图像描述，再对对象 `+4` 指向的 `{payload, length}` 调用 `0x10204B7C`。5 个局部案例覆盖正常申请、申请失败、池不可用及由 metadata `+0xED` 控制的池 16 回退。回退请求大小为 `0x276C000`，本函数此分支没有执行相同的缓存调用；不能假定所有分配都有相同同步行为。

效果组织函数 `0x100A5472` 在索引 0、6 等分支调用这个申请器，将对象放入图像上下文 `+0x30C`，再将对象内嵌的 **`object +0x18` 图像描述结构** 交给 `0x100A535A` 绑定输出，随后提交效果任务。处理返回后设置对象 `+0x14` 标志。原厂已区分对象句柄、图像描述结构和像素地址，LUT 不能把三者混用。

另一个后处理阶段 **`0x100A5BD2`** 会把上述输出描述结构送入通用图像处理服务，再释放图像对象。对没有附加工作缓冲、类型为 0/2 的人工作业，实际执行顺序是：

1. `0x100E9CAE(1, config, 0x100A0E87)`，等待事件 `0x10`，清除事件。
2. `0x100E9B08(0xD, config, 0x100A0E87)`，等待事件 `0x20`，清除事件。
3. `0x10142B50(object)` 归还图像对象，清空上下文 `+0x30C`。

有附加工作缓冲的静态分支还可选择服务模式 `0xF`；本轮没有执行该分支。两次等待均传入 3000 的超时参数。返回 0 或 1 的替换等待服务得到相同的后续释放顺序：这个函数没有据等待返回值阻止释放。**这是局部控制流证据，不是实机超时故障的复现，也不等于所有作业类型都在此释放。**

这两次服务是图像后处理，不能称为 JPEG 编码。实际回调 `0x100A0E86` 将 `0x4218300C` 转为事件 `0x10`，并按上下文将 `0x42183009` 转为事件 `0x20/0x40`。此外，上一轮停止点 **`0x1020182C` 实际是加锁后的消息入队包装**，底层使用 `0x1021157C`；未到 MMIO、DMA 或硬件寄存器层。

### 缓存：小范围合同确定，大范围特权服务待恢复

| 原厂函数 | 小范围分支的 CP15 指令 | 作用 |
| --- | --- | --- |
| `0x10204B0C(ptr, length)` | `MCR p15,0,r2,c7,c10,1` | clean |
| `0x10204B48(ptr, length)` | `MCR p15,0,r2,c7,c6,1` | invalidate |
| `0x10204B7C(ptr, length)` | `MCR p15,0,r2,c7,c14,1` | clean + invalidate |

指令含义与 [Arm 缓存维护说明](https://developer.arm.com/community/arm-community-blogs/b/soc-design-and-simulation-blog/posts/exploring-how-cache-coherency-accelerates-heterogeneous-compute)一致。三个函数先调用 `0x102185C2` 判断地址区域策略；允许维护且长度不大于 `0x45000`（282,624）字节时，从 `ptr & ~63` 开始，每次增加 64，直到达到 `ptr + length`，最后执行 `DSB SY`。非对齐指针且长度为零时仍可能处理首行，不能把此函数当作天然的零长度空操作。

超过该阈值，三个函数均进入 `0x10035AD0(3, 2)`。它通过 `BX PC` 切换至 ARM 状态，在 `0x10035AE4` 执行 **`SVC #6`**；IP 中传入的服务标识是 `0x010B0211`。这尚未被证明是函数指针，不能把这个数值直接作为地址查找实现；相邻 SVC 包装器也将类似常量放入 IP。**当前不能仅按包装器名称宣称完成全缓存刷新，也没有恢复多核/外层缓存同步。** 地址策略还依赖运行时表 `0xC2A1BE00`，本轮未取得机身初始化后的真实值。

21 个缓存案例只替换地址策略和特权服务，并拦截 CP15 指令，检查原厂计算的行地址、边界长度和分支；没有模拟缓存效果。文件读取附近另见 `0x10340564` invalidate → `0x10340570` 读取 → `0x10340578` clean 的静态顺序，但尚未将这一段和软件 LUT 输入交接完整绑定。

对 LUT 的直接要求是：确认解码/DMA 完成及输入所有权后，才能让 CPU 读入；输出必须在后续原厂处理/编码启动前写完并完成恰当的同步。不能在效果任务提前返回后让后台继续修改原厂可能已经回收的缓冲。主图会超过上述维护阈值，不能用小块测试替代主图缓存合同。

## 第四轮：保存作业的阶段表、主图交接与 JPEG 组装

新增 `tools/trace_lut_save.py`，把第三轮分开的处理和编码合同放进同一个人工作业。**本轮确认普通修饰的保存作业会保留效果主图，进入主图编码后再清理；还将原厂 JPEG 组装描述接入原厂分段写入器。** 仍然没有从真实 JPEG 解码执行到 SD 副本提交，下面明确列出每处替换和停止边界。

### 预览和保存采用不同阶段表

`0x1038F406` 将修饰后端对象交给 `0x1021ED34`，后者调用 **`0x102218D0`**。构造器申请 `0x2CC` 字节控制对象和 `0x4740` 字节作业，复制处理索引、参数和输出描述结构，再经 `0x10221C7E` 选择阶段表。

对操作 1/5/6/7，实际执行构造器得到：

| 请求后端 `+4` 的阶段类型 | 作业字段 | 选择的表 | 普通修饰的区别 |
| --- | --- | --- | --- |
| 0 | 作业 `+0x4690=0` | `0xC18872D0` | lane 0 只有阶段 0–4，表内没有阶段 5 的主图编码 |
| 1 | 作业 `+0x4690=1` | **`0xC1889684`** | lane 0 具有阶段 0–9；效果处理在阶段 4，主图编码在阶段 5 |

这里的预览/保存称呼由先前构造器到后端的连接和本轮表内容共同支持，不按表地址猜测。操作 `0x11/0x12/0x15/0x16` 及类型 2 有其他选择规则，不将普通修饰结论推广到全部模式。

阶段表是 **11 lane × 15 phase 的指针矩阵**，由 `0x1007FF16`、`0x1007FC12` 等调度代码读取；非空项 `+0x14` 指向本阶段子步骤表。子步骤每项 12 字节，包含控制字节、可选前置函数和处理函数。**`0x100CCDC4`** 按工作对象 `+0x24` 游标读取最多 20 项，调用处理函数；返回 0 前进、返回 2 重置游标并返回，其余值结合控制字节/取消状态重试或结束。这不是简单的裸函数地址列表。

保存表 lane 0 中相关静态阶段为：

| 阶段 | 已恢复的原厂子步骤 |
| --- | --- |
| 4，子表 `0xC1888DC4` | `0x100A577E` 效果分支 → `0x100A578C` 派生图对象准备 → `0x100A5BD2` 效果后处理 → `0x100A42C8` 压缩缓冲准备 → 其余派生图处理 |
| 5，子表 `0xC1888EDC` | **`0x100A60F2` 主图编码 → `0x100A63B0` 主图清理** → `0x100A68D4` 派生图编码 → `0x100A691C` 派生图清理 |
| 6 | `0x100A69C2` 通知上层编码阶段完成 |
| 7 | `0x100A6A54` 准备头部工作区 → `0x100A6C2C` 组织图像/元数据并提交组装 |
| 8–9 | 原厂上层通知/等待、资源清理；lane 1 另有配合步骤，尚未完整执行 |

阶段 1–3 的部分子表位于 BSS（如 `0xC235E778`），当前 stock EG 中没有它们运行时构造后的内容。工具将这些项明确标记为 runtime，不把零值当成真正的空处理链。这也是尚未从阶段表接通原始 JPEG 解码的具体缺口。

### 同一个作业里的主图保留、编码与归还

连续探针保留同一个作业、上下文和图像对象，实际执行上述子步骤解释器：

1. 在阶段 4 从子步骤 0 开始。原厂效果组织器申请输出对象，绑定 `object+0x18` 图像描述，再提交效果。申请器和效果任务被替换；效果桩在输出 Y/C 区写入不同哨兵字节，不执行 LUT。
2. 执行 `0x100A5BD2` 的**类型 1** 分支，替换通用图像服务及事件服务。它将派生图标志更新后保留上下文 `+0x30C` 的主图对象。到阶段 4 子步骤 3 `0x100A42C8` 前主动停止。
3. 夹具提供已准备的压缩输出对象，跳过阶段 4 剩余派生图步骤，再将同一个阶段工作对象切到原厂阶段 5 子表。这里是夹具驱动阶段推进，未执行真实调度器。
4. 实际执行 `0x100A60F2 → 0x10096EE6 → 0x100978A4`。codec 边界检查收到的两个平面正是效果输出平面，哨兵仍在。codec 本体被替换，只写入人工状态、压缩目标地址及长度。
5. 实际执行原厂结果回传和 `0x100A63B0`，随后才进入图像归还边界并清空上下文 `+0x30C`。到阶段 5 子步骤 2 `0x100A68D4` 前停止，派生图编码未执行。

8 个案例覆盖效果索引 0/6、格式 1/2，以及人工 codec 成功/失败。证明的是**同一对象和同一平面在选定原厂步骤间的传递顺序**，不是 CPU 缓存一致性或真实图像颜色正确；两个主动停止的执行没有完成函数返回，工具不对其宣称寄存器/栈返回合同通过。

错误分支还有一条重要限制：在这段人工路径中，即便 `0x10096EE6` 返回失败、局部结果状态为 1，`0x100A60F2` 仍会设置压缩对象 `+8=1`，复制部分结果字段，后续清理仍会归还主图。它没有在紧随调用的位置检查这个返回值。**“已编码”标志、非零长度或主图已经释放，都不能作为 LUT 保存成功的单独判据。** 尚未恢复完整上层错误传播，不能据此认定实机一定会保存损坏文件。

### JPEG 组装已经连接到原厂写入器边界

**`0x100A6A92`** 将原厂压缩对象组织成组装请求。JPEG 类型下，请求指向主图压缩描述 `owner+0x40`、可选派生图、元数据、头部工作区和原照片句柄。

`0x1033DF24` 是到 **`0x102B351A`** 的跳板。后者按组装模式调用处理体；模式 0 进入 `0x102B35AA`。这一步是**组织头部与压缩图像的组合描述，不是直接进行 SD 写入**。原厂给主图压缩长度减 2，并把头部和各图像段长度累加到组装对象 `+0x18` 的 64 位总长度。

两组人工长度 1234/65536 的探针实际执行请求构造、组装模式分派和上述长度计算，只将元数据序列化 `0x102B33BE` 替换为固定的 `0x120` 字节头部。随后继续在同一夹具中执行：

- `0x102B688E(mode=0, object, kind, result)`：主图段返回 `compressed+2`、`length-2`、零填充；头部段返回独立头部区；不存在的派生段被略过。
- **`0x102B6EC0(fd, 0, object)`**：沿原厂段顺序读取这个组装对象，进入文件服务 `0x102C8DC6`。该边界被内存接收器替换，实际收到的字节严格等于 `header + compressed[2:]`。
- 文件边界人工返回 `0xA0000002` 时，原厂写入器返回 2 并停止后续写入。未执行关闭、删除残留副本、DCF 提交或文件登记。

本案例故意使用不可解码的人工头部与压缩字节，避免将夹具构造出的 JPEG 冒充原厂 codec 输出。只记录内存中的字节比对，没有创建照片文件。已经连接的是**codec 输出对象形状 → 原厂组装描述 → 原厂写入器参数**，真实 EXIF/方向、预览和缩略图仍需保留原厂序列化结果后验证。

### 后端“完成”信号的实际含义

**`0x1021ECD4`** 汇总作业，更新图像上下文错误字段，调用上层回调，然后释放 `0x4740` 作业和 `0x2CC` 控制对象。4 个案例实际执行它与原厂 `0x1034001C` 回调的连接：

- 后端没有通用作业错误，且作业 `+0x472C=1` 时，发送事件 `0x100`。
- 其他人工组合发送事件 `0x200`。

`+0x472C` 来自效果提交包装器 `0x100CCA42` 的返回值；它首先表示提交/等待路径成立，并非 codec 结果长度或像素处理结果。结合上面的错误案例，**此“完成”事件也不能单独证明 JPEG 已正确编码并完成文件提交**。需要恢复并检查完整分层状态。

## 第七轮：模式 3 解码链与效果输入的同一性

新增 `tools/probe_lut_decode_chain.py`，结果位于 `build/research/lut-postprocess/decode-chain.json`。本轮实际执行了第六轮找到的上层链：`0x10340766` 模式 3 → `0x10340440` → `0x10390DCC` → codec 消息 `0x42181802`，并把同一准备结构送进保存描述符后缀与效果初始化器。37 个有界案例通过。仍然没有解码真实像素、没有访问相机。

### 模式分派合同

`0x10340766(state, preparation, metadata)` 按 `preparation+6`（半字）分派：0 → 带元数据的另一包装 `0x10390E6E`；2/5 → `0x103406CC`；**3 → `0x10340440`（解码准备）**；1/4/其他 → 直接返回且不碰 `state+0xE`。两个执行证据支持"模式 3 是保存路线的默认解码模式"：

- `0x1034096A(preparation)` 计算 `preparation+6`：仅当 `preparation+4`（半字）与 `preparation+9`（字节）取特殊值（+4==0 且 +9==1；+9==2；+4==4 且 +9==1）才得到 0 或 5，**其余全部返回 3**。
- `request+8==2` 的另一条路线在 `0x10344A54` 直接写 `preparation+6 = 3`（r8 常量），并在 `0x10344BA2` 第二次调用 `0x10340766`。

`0x10340440` 把准备结构装入 0x18 字节包装参数（`+0`=压缩源 `preparation+0xC`、`+8/+0xA`=宽高 `+0x2E/+0x30`、`+0x10/+0x14`=目标 Y/C `+0x20/+0x24`），并**硬编码格式字节 2**（`movs r0,#2; strb [sp,#0xC]`）。`0x10390DCC` 返回非零 → `state+0xE=0` 且函数返回 0；返回 0 → `state+0xE=1` 且返回 1。

### 解码包装器 `0x10390DCC` 的完整合同

config 为 `0xC295C230+0xB8 = 0xC295C2E8`，先清零 0x44 字节。字段：`+0x10` = 压缩源地址；`+0x18/+0x1C` = Y/C 步长，都等于**宽度向上对齐 16**；`+0x20`（字节）= codec 格式：包装字节 2 → 1，3 → 2，其他 → 1（经模式 3 路径时恒为 1）；`+0x24/+0x28` = 目标 Y/C 平面。**高度不进入 config**——codec 从 JPEG 流自行取得。执行顺序：`0x10204B48(目标Y, 0x3FC300)` invalidate → 清事件 `0x90`（`0x103400E0`）→ `0x102193D2(sp)` 提交（消息帧 `+0xC`=回调 `0x1034001D`、`+0x10`=0x42181802、`+0x14`=config、`+0x18`=0）→ 等事件 `0x90`（`0x103400D0`）。失败判定：等待返回值 bit `0x80` 置位，或 `config+0x2C == 1`（严格等于 1；2、0xFF 都按成功处理）。

### 准备结构尺寸的来源：两级取整

`0x1034080A`（`0x10340920` 调用的变体选择器之一）尾部：把 `[state+0x3C]+0x39C/0x39E`（照片实际宽高）写入 `preparation+0x32/0x34`，再调 `0x10340486(mode=preparation+6, state+8, &prep+0x2E, &prep+0x32)`。`0x10340486` 对模式 3（或 `request+0xA>=4`）把**宽度向上取整到 16、高度向上取整到 8** 写入 `preparation+0x2E/0x30`；`request+0xA<4` 且模式 5 只原样复制；否则不改。之后 `0x103450CC` 再用同一函数从 `sp+0x52/0x54`（来自 `request+0x58/0x5A`，`request+0xA==1` 时改源 `[sp+0xC]+0x22/0x24`）重算一遍供描述符使用。两处取整结果一致。

### 平面绑定与对象所有权（0x103441A0 路线）

保存主路线在 `0x10344F82–0x10344FA0` 实际执行：`0x103A2070(request+0xA 字节, request[0])` 的返回值同时写入 `preparation+0x10/0x14`，**该字段非零是 `0x103441A0` 的前置条件**，否则置 `request+0xC=1` 返回。`0x103441A0` 内部：

- `preparation+0xC` = `0x103917F6(request[0])` = **`[[desc+4]]`** 双重间接，其中 `desc = 0x10146DB0(request[0], 0x3A, 上下文)`，缓存于全局 `0xC29664E0+0x28`（状态字节 `+0x2C=2`）。
- `preparation+0x20/0x24` = 池对象 `0x103917A2(request[0], 上下文)` 的 `+0x2C/+0x30`；该对象同时存入调用者栈 `+0xC`。
- 后续使用/释放的"跟踪对象"取自全局槽 `0xC29B30D8+0x3C0`（`0x10391F9A`）；为空时经 `0x103917C4 → 0x10143A30` 新申请并写回（`0x10391F92`）。`request+0x5C/0x60` = 跟踪对象的 `+0x2C/+0x30`，跟踪对象指针存栈 `+0x118`。池对象与跟踪对象可以不同——执行验证了这两条路径。

`0x103917A2` 全局缓存在 `0xC29664E0`（`+0x1C=2` 命中 `+0x18`）；未命中走 `0x10142A78(owner, metadata)`：池 8（`0x10141C94` 查询、`0x100CC512` 申请），不可用时若 `metadata+0xED!=0` 回退池 16、请求大小 **0x276C000**；`0x1014237A` 初始化内嵌描述符（本轮以桩替代，对象 `+0x2C/+0x30` 平面由夹具预设）；随后对对象 `+4` 指向的 `{payload, length}` 做 clean+invalidate（`0x10204B7C`）。

### 错误路径与错误码分层

`0x10344828` 序言：`sl = 0xC18CA75C` 且 **`[sl+0x14] = 0`（进入即清零）**，`request+0xC` 与 `state+0xE` 清零，常量 `r5=1、r8=3、fp=2、sb=0`。图像上下文 `sp+0xD0 = 0x10211F4C(0x1280, 0)` 清零后 `+0x3A4 = r7`（大上下文）——即第六轮后端 `0xC295BD18` 的真实身份。四层检查全部执行验证：

| 检查点 | 条件 | 结果 |
| --- | --- | --- |
| `0x10344FF4`（`0x10340920` 之后） | `state+0xE != 0` | 释放 `sp+0xD0`，`request+0xC = state+0xE` 原值，退出 |
| `0x10345012`（`0x10340766` 之后） | `state+0xE != 0` | 释放 `sp+0xD0`，`request+0xC = 1`，退出 |
| `0x10345022`（`request+0xA==1` 分支）/ `0x103450D0`（提交效果前） | `[0xC18CA75C+0x14] != 0` | `request+0xC = 3`；后者的清理路径释放全局对象、源描述符和 `sp+0xD0` |
| `0x10345128`（后端返回后） | 返回值非零 | `request+0xC = 返回值`，经 `0x1034513C` 清理后为 1 |

两个执行发现：**全局标志错误码 3 会穿透清理**——`0x10345164` 跳到 `0x10344970`，那里只有 `b 0x1034494A`，跳过了 `0x1034496E` 的 `strb r5`；清理中的 `0x10391F9A` 检查在 `0x1034513C` 出现两次，非零时经 `0x103917EC → 0x10143AE8` 释放全局对象并把全局槽清零（`movs r0,#0; bl 0x10391F92`）。所有错误路径均不进入后端调用（探针以钩子断言后端与初始化器零进入）。

### 描述符后缀与初始化器的地址连续性

单个夹具、同一栈帧内连续执行：绑定块 → 取整 → `0x10340766` 模式 3 → `0x10345012` 检查 → 描述符后缀 `0x103450DC`（在 `0x1038F64A` 边界停止）→ 完整返回 `0x1038F91E`。三种几何（32×16、33×17、5568×3712）× 操作 5/6/7。描述符合同：`+0`=1（r5 格式码）；`+2/+4/+6` 都是 `preparation+0x2E`（对齐后步长）；`+8`=`preparation+0x30`（对齐后高度）；`+0xA/+0xC`=原始宽高；`+0xE/+0x10`=0；`+0x14/+0x18`=`preparation+0x20/0x24`。后端实参 `(sp+0xD0, 栈+0xF0, 0, request+9, [sp]=request+0x2C)`。初始化器把该描述符指针写入参数 `+4`。

**验收结论（阶段 A 核心项）**：在同一原厂调用路径中，选定 JPEG 的压缩源（`preparation+0xC → config+0x10`）、解码目标（池对象 `+0x2C/+0x30 → preparation+0x20/0x24 → config+0x24/0x28`）与效果输入（同一 `preparation+0x20/0x24 → 描述符+0x14/0x18 → 参数+4`）是同一组对象；错误路径不进入效果处理；每处替换边界（codec、事件、缓存、池、查询）在 JSON 事件流中逐条标明。

## 第八轮：颜色合同决策、LUT 核心与试验固件

### 颜色合同的静态边界与决策（阶段 B）

对解码输出平面颜色合同的静态追查到硬件边界为止：解码消息处理器 `0x10219634` 只做消息转发，颜色约定固化在 JPEG 硬件 codec 内部；ROM 中不存在软件 YCbCr→RGB 例程（BT.601 定点常数全 ROM 扫描无命中）；调试转储 `YCbCrFormat = %d`（`0x100BA470`）与回放缓存名 `mip%05d.ycc`（`0x100BA984`）证明 `.ycc` 平面格式是一等公民但枚举语义未打开。据此决策：**转换常数全部集中在 `z30_extensions.lut` 一处**（默认 JFIF/BT.601 有限范围、Y 16–235、C 16–240 中心 128），真机用受控色卡验证后只调一个模块；交错对内 Cb/Cr 字节顺序同样挂起真机验证。缓存维护直接调用原厂 `0x10204B48/0x10204B0C`（整帧长度走 SVC 特权路径），输入读前 invalidate、输出写后 clean。

### LUT 核心（阶段 C）

`z30_extensions.lut` 提供主机端完整实现与相机二进制合同：

- `.cube` 解析子集：3D 表（2..65）、共享 DOMAIN_MIN/MAX、红通道最快的数据顺序；1D 表、未知指令、行数不符、域反转、值越域全部拒绝。21 个单元测试覆盖解析、插值钳制、中点、通道交换、二进制往返与 YCbCr 往返。
- 相机二进制 `WL3L` v1：22 字节头（magic/版本/尺寸/域六端点，0..65535 刻度）+ size³×3×u16。
- 整数定点合同（`*_int` 函数）：正向 Q8.8（1193/359/88/183/454），反向 Q2.14（4208/8262/1604 等），ARM 核心与主机逐位一致。

### 钩子设计与实现（阶段 D）

操作初始化表 `0x115CD6CC` 按 `op*8` 索引、op 0x20 结束、0x21 起是系数数据——不加新操作号。**钩子点选定为 index-6 处理函数入口 `0x1025FB8E`**（worker `0x100CC910` 经描述符 `+0x14` 调用它，参数对象为静态 `0xC295BE94`：+4 输入描述符、+0x10 输出描述符、+0x14 结果 0/1；模式/强度在 +0xC/+0xD）。gate 复制被位移的 `cmp/push/beq/mov/bl` 五条指令，标志字非零走 LUT 核心、为零原样落回 stock（远调用经 r12——追加区距 stock 代码 31.6 MB，超出 Thumb BL ±16 MB，直接 BL 会被 Keystone 静默编码错误，这是本轮踩过的坑）。

`z30_extensions.features.lut_core` 生成 Thumb-2 核心：验证描述符（格式 1、宽高一致、x0 偶数）→ 原厂 invalidate 输入平面 → 逐像素 BT.601 有限范围转换 → 打包三线性查表（u16.16 权重、逐项 `>>16` 累加）→ 反向转换 → 色度对平均（4:2:2）→ 原厂 clean 输出平面 → 返回 1/0。`lut_lookup` 独立成函数（r7=块指针），坐标先钳制进域再无符号 `udiv`。

### 接口与内存

- 加载器入口 `sd_load(control, workspace)`，返回 0 成功、1 打开失败、2 I/O/关闭失败、3 格式或解析失败、4 内存边界/输入容量不够。控制块依次为 flag、活动 WL3L 绝对指针、最近状态、活动 payload 长度；workspace 为输入指针/容量、候选输出指针/容量、路径指针，共五个 word。
- `build_layout()` 只返回偏移；`build_block(binary, address)` 要求传入明确的 RAM 基址并生成绝对地址。没有把固件 append 区当作可写工作区。默认输入缓冲 8 MiB、候选槽 `1,647,776` 字节，17³ 内嵌表时整个示例 arena 为 `10,065,940` 字节。真实池分配、容量与生命周期未验证；该布局不是运行时分配器。

- 输入、候选输出、控制块及活动 payload 的范围检查防止读文件或解析覆盖当前有效表。调用者仍须提供有效映射、可信 workspace/path，并在整个调用及处理期间持有相关内存、串行化操作；当前没有任务锁或多读者引用计数。

### 解析合同

文本按行解析，支持不区分大小写的 `LUT_3D_SIZE`（2..65）、`DOMAIN_MIN/MAX`、TITLE、整行注释、CRLF/LF、空白及没有末尾换行。每个数据行必须恰有三个数，节点数必须为 size³。关键指令在数据前，重复 size/domain、未知指令、额外节点、域外值、空域和量化后折叠的域均拒绝。文本数值限定十进制 [0,1]、最多九位小数，可用前导点或符号；指数记法及更高精度拒绝。主机解析器支持的文本范围更宽，不能声称两端接受集合完全一致；此类文件可在主机转换为 WL3L。

数字使用 1e9 标度精确十进制整数；节点归一化使用 64 位乘积和 32 位长除法，按最近偶数舍入到 u16。没有草稿中近似小数权重、蓝通道槽冲突、size³ 校验和返回长度错误。浮点主机参考在精确半格边界可能因二进制浮点近似差 1 LSB，因此验证报告只对所测文本声称与 `pack_binary` 逐字节一致；整数舍入另用 `Fraction` 独立核对。

WL3L 分支校验 magic、version=1、size、reserved=0、三个严格递增域，以及精确文件长度/输出容量，再复制 payload。最大 65³ 二进制 `1,647,772` 字节已验证，65³ 恒等文本也已完整加载并与主机打包结果逐字节核对。8 MiB 是明确文件容量，不保证所有以任意长小数/注释书写的合法 65³ 文本都可装入；超限返回容量错误。

## 第十轮：动态内存会话、处理互斥与失败资源保留（2026-10-29）

### 原厂堆接口的证据

`0x10211F4C(size, pool)` 按 `0xC1F8A208 + pool*20` 取堆句柄，再经 `0x10211FF2` 调 ARM 包装器 `0x10036150`，最终 SVC #6（`0x10036160`，服务标识 `0x80470400`）。SVC 参数是句柄、尺寸、输出指针地址和 0。包装器将 SVC 非零状态转换为 NULL；成功返回输出指针。这里的服务标识不是函数地址。

`0x10211F5E(pointer)` 遍历两个地址区间，按所属堆调用 `0x10211FEC → 0x1003630C`；后者先用 Thumb `BX PC` 转 ARM，再在 `0x10036320` 执行 SVC #6，标识 `0x80480200`。成功返回 0，失败返回服务状态。若地址不属于两个区间，原包装器不进入 SVC，返回未改动的 pointer；不能只因函数返回就认为已释放。

9 个有界案例实际执行上述原厂包装器、ARM/Thumb 切换和 SVC 前后代码，只替换 SVC 结果与区域表，验证两个池的分配/释放成功和失败，以及区间外地址。并未执行真实内核分配器。

另有静态启动证据：`0x100530D6–0x100530E2` 从 `0x114A32C4` 复制两条 12 字节配置并调用 `0x10211EF8`；配置内容为 General=16 MiB、Heap=25 MiB。前者是当前分配参数 pool=0 的配置容量，不是运行时空闲量，也不保证存在所需连续块。

### 会话 ABI 与生命周期

调用者需提供对齐的、有效的 48 字节 RAM 会话，`build_session(fallback_address, fallback_length)` 生成初值。会话管理器代码入口 +0 为 load/reload(session,path)，+4 为 reset(session)。

| 偏移 | 所有者/用途 |
|---|---|
| +0/+4/+8/+12 | 与加载器共用的 flag、活动指针、状态、活动长度 |
| +16 | 当前由堆分配的活动 payload；内嵌 fallback 时为 0 |
| +20 | 未能释放的输入暂存分配 |
| +24 | 加载、重载、重置、像素处理共享的锁 |
| +28/+36 | 内嵌 fallback 地址/长度，必须始终有效 |
| +32 | 未能释放的旧 payload 或失败候选分配 |
| +40 | 本次操作是否已经提交活动指针 |
| +44 | 待关闭句柄；0xFFFFFFFF 表示无，句柄 0 也属于有效值 |

管理器使用原厂 pool 0 分配输入与候选，不把 append 区作为 RAM。输入默认从 64 KiB 起，在文件超过容量时，先关闭文件、释放旧输入缓冲，再倍增并重新打开读取，最大 8 MiB。候选槽仍按最大 65³ 分配约 1.65 MB。这样小表无需固定占用 8 MiB；成功后输入暂存被释放，仅活动表保留。重载时另分配候选，成功激活后再释放旧表。reset 恢复内嵌 fallback，再释放活动堆表。

释放失败的指针保留在 +20/+32，下一操作先重试回收；未完成清理时不继续分配。状态 0..4 沿用加载器；5 为分配失败；6 为忙；7 为资源仍待回收、没有本次新提交；8 为已提交但清理待重试。状态 8 时新活动表已经有效，不能当作“重载失败且仍用旧表”，应同时查看 +40。忙返回 6 时不改写另一个操作的状态、锁或提交标志。

单独加载器也补齐关闭失败合同：返回 r0 状态，同时以 r1 返回尚未成功关闭的句柄，无句柄为 -1。会话将其保存在 +44，下次先重试关闭，成功之前不重新打开文件。容量溢出路径的 close 失败改为 I/O 错误 2，避免管理器误当作可扩容重试。这里只证明关闭尝试及句柄归属，不能把“调用过 close”描述为“文件已成功关闭”。

`lut_core.build_lut_core(..., active_payload=True, session_lock=True)` 通过 LDREX/STREX 有界尝试获取 +24 的锁，在整个核心调用及状态写回后释放。忙时返回处理失败，不访问活动表、不改输出、不释放持锁者；描述符校验失败也会解锁。默认内嵌模式与不带 session_lock 的动态模式保持原 ABI。

## 第十二轮：真机首测与读取上限缺陷（2026-10-29）

### 真机结果

第一次上机用的是 `output/lut-sd-menu-v2/EG209020.BIN`（SHA-256 `4AC868E8…`）。菜单进入正常，四项动作都能选；17³ 文本表（132,684 字节）报「无效的 LUT」（状态 3），2³ 文本表（247 字节）与 2³ 二进制表（70 字节）都报「SD LUT 已就绪」（状态 0）。删除文件后仍报状态 3，而不是「找不到文件」。

### 根因

`sd_load` 在输入缓冲写满时用一次 1 字节探测读判断后面还有没有数据（`sd_probe`）。真机上这次 1 字节读返回 0，被当作文件结束，于是 64 KiB 之后的输入被截断；解析在行中途撞到输入结尾，报状态 3。缓冲增长路径（状态 4）因此从未触发——它只在文件超过缓冲时才有用，而探测先一步把结论改成了 EOF。小表不进探测分支，所以正常。

### 修改

删掉探测：缓冲写满即报状态 4，由会话按 64 KiB → 128 KiB → … → 8 MiB 倍增后重新读取。代价是「恰好填满缓冲」的文件多一次分配与重读；夹具 `exact_input_capacity` 的期望由 0 改为 4，成功路径改由会话的增长重试覆盖。新镜像 `output/lut-sd-menu-v3/EG209020.BIN`，33,999,490 字节，SHA-256 `57F7CCA661BC5A2E3C84842FAC0AB8930FEA04DEA90540580B57ACD0E9F296CD`，镜像验证 29 个案例通过。

### 仍未解释

删除文件返回 3 而不是 1。打开失败的错误码约定与夹具假设（返回负值）不符：真机很可能返回 0 或正值，被当作句柄继续使用，随后的读返回 0 字节，于是落到状态 3。暂不改动，因为只有一条证据；若后续确认，把 `blt` 换成 `beq`/`ble` 即可。
