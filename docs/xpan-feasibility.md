# Z30 C1.20：参考 Z8/Z9 方案实现 65:24 照片裁切

> 2026-10-17 最新复测更正：4:3、5:4 在 v8 下仍出现整幅横向压缩，且存在间歇性表现；撤回此前“v8 已修复”或“全部画幅实机通过”的结论。其余四种宽画幅据用户反馈正常。全尺寸 DX 横向裁切尚待真实拍摄管线验证，以下历史成功反馈不作为当前验收结论。


日期：2026-10-17。当前交付包含静态定位和原厂函数的 Unicorn 隔离执行，没有改写固件文件、访问相机或执行 QEMU。

后续进展：[多画幅研究与 63 个原厂几何案例](aspect-profiles-research.md)。后续已生成独立模拟器研究 EG，覆盖同步裁切与输出参数；本页下文保留早期单表修改实验的时间边界。

## 结论

值得沿 Z30 原厂照片图像区域通路研究。原厂已经支持 DX、1:1、16:9，比从零新增照片处理管线更有依据。但尚未恢复区域枚举到裁切、JPEG、NEF、取景和文件元数据的完整关系，不能宣布只需五处修改，也不能直接移植 Z9 地址或 DSID。

建议先在独立实验构建中借用现有 16:9 档验证 XPAN，再考虑新增第四档。借用会改变该实验构建的 16:9 行为；正式版本需保留原有功能并提供独立选项。此前的 [实时取景遮幅方案](aspect-mask-feasibility.md) 只处理显示，不能作为照片裁切的实现证明。

## 参考文档中需要重新验证的假设

- `8256×5072` 约为 1.628:1，不是 16:9；而 `5072=5504-432`。四元组可能包含端点或其他内部坐标，不能仅凭外观认定为 `(x,y,w,h)`。
- 标为 5:4 的 `(1376,0,6880,5504)`，如果按宽高解释，左右边距不对称。应恢复原始表、索引和读表代码后再判断。
- `DSID 15`、`0x1600000F` 和 LimitSelectableImageArea 的编号都是参考机型线索；这里未确认其在 Z30 上的身份。属性键也不能当作 RAM 地址直接写。
- RAM 可写、设置值接受及无崩溃，只能证明对应执行路径未显现错误，不能证明拍摄路径真正消费了新裁切值。
- Z30 仓库已有输入身份校验和容器处理机制；参考文档的“XOR + SHA-1 签名”未提供 Z30 证据。摘要、CRC 与密码学签名需分别核实；容器回环成功不能证明可刷或硬件安全。

## 本次 Z30 原始固件定位

输入：仓库 `Z_30_0120.bin`，由现有 `extract_eg` 校验并解码，再经 `StockImage` 检查 EG 身份、CRC 与 scatter 映射。

EG：33,939,514 字节，SHA-256：`8a99ced2d8220729ba067587b0624bf30c81757abc5d728768134b1c7fd457fa`。

复现：在项目目录运行 `python tools/inspect_xpan.py`。输出 [静态扫描报告](../build/research/xpan-stock-scan.json)。这是字节扫描，指针匹配也不是已恢复的调用链。

官方尺寸依据：[Nikon Z30 技术规格](https://onlinemanual.nikonimglib.com/z30/en/15-08.html)。原厂 16:9 输出本身存在像素量化，不应要求标称比例在整数像素上完全精确。

## XPAN 几何目标

以官方 DX 大尺寸 `5568×3712` 为最终照片坐标参考：

```text
理想高度 = 5568×24/65 = 2055.876923…
候选输出 = 5568×2056，约 11.45 MP
候选居中区域 = (0,828,5568,2056)
比例误差约 -0.0060%
```

这是几何目标，不是已验证的固件字段值。2056 为 8 的倍数，不能因此推定它满足原厂 ISP/JPEG 全部对齐要求；内部坐标还可能含光学黑区、边缘像素和缩放。若要整数像素严格 65:24，`5525×2040` 满足比例但失去全宽且宽度为奇数，同样不能直接采用。

中、小尺寸需分别恢复原厂缩放和对齐规则，不能仅用大尺寸除以比例复制到所有表。第一轮限制 JPEG 大尺寸，是为缩小验证范围，不代表固件已具备隔离这些模式的能力。


## 后续：原厂函数隔离执行

运行 `python tools/probe_xpan_geometry.py --deps build/verify-deps`，需要可用的 Capstone 与 Unicorn。报告：[xpan-native-geometry.json](../build/research/xpan-native-geometry.json)。探针使用现有 `native_runtime.Context`，加载原始 EG 和初始化数据，在合成 RAM 中构造对象与输入。没有加载真实拍摄上下文或启动相机任务；运行时基础设施还会跳过已有日志入口。

18 个案例全部通过：DX / 16:9 / 1:1 × L/M/S × 原始状态 / 只改输出高度。每个案例执行实际 Thumb 函数，并检查返回、栈和被调用者保存寄存器；缓冲区函数的实际读表地址也有记录。

### 已恢复的入口和索引

| 入口 | 已验证行为 |
|---|---|
| `0x1020BFDA(area,size)` | 从 `0xC18C7DFC + area*4` 取表指针，再按 `size*4` 返回尺寸对地址；`area=0/2/4` 分别返回与 DX / 16:9 / 1:1 官方尺寸一致的表，`size=0/1/2` 对应 L/M/S |
| `0x1020BFC8(0,area,size)` | 另一组内部尺寸选择器；大尺寸三个区域分别返回 `5600×3728`、`5600×3144`、`3728×3728` |
| `0x1020C072(area)` | 返回偏移候选：三个区域分别是 `(0,0)`、`(0,292)`、`(936,0)`；尚未证明其硬件坐标身份 |
| `0x10142BEA(object,info)` | 本次合成输入走 `info+0x208` 区域索引和 `info+0x229` 尺寸索引，调用 `0x1020BFDA`，生成输出尺寸、对齐尺寸、步幅和布局字值 |
| `0x1014237A(object,info,0)` | 在本次零初始化输入分支生成另一份尺寸与偏移配置；16:9 大尺寸对象 `+0x22/+0x24` 为 `5568×3128`，`+0x26/+0x28` 为 `(16,300)`。字段用途仍以候选标记，不宣称已提交给 ISP |

`0x105971B4` 虽含 `0x10750908` 字值，已检查的 `0x10597120` 使用点先减 `0x26`，再读取更前面的项目。不能把这一个字值引用当作尺寸三元组已被直接消费的证明。

### 单表修改的反例

只在模拟器内存把 `0x115A4DB6` 的 u16 从 3128 改为 2056，结束后恢复；不输出修改后 EG 或容器。

| 结果 | 原厂 16:9 L | 只改输出高度 |
|---|---|---|
| 输出尺寸选择器 | `5568×3128` | `5568×2056` |
| 缓冲区对齐尺寸 | `5568×3136` | `5568×2056` |
| 步幅 | 8352 | 8352 |
| 内部尺寸选择器 | `5600×3144` | `5600×3144` |
| 偏移选择器 | `(0,292)` | `(0,292)` |
| 配置对象 `+0x22/+0x24` | `5568×3128` | `5568×3128` |
| 配置对象 `+0x26/+0x28` | `(16,300)` | `(16,300)` |

XPAN 实验的配置对象并非全部不变：`+0x31/+0x54/+0x55/+0x58/+0x59` 字节随输出高度变化，但上表中的尺寸与偏移字段保持原厂值。另 8 组配置对象和缓冲区对象均保持相同。探针对这些关系做断言。这说明同一配置通路内也存在分别取值的几何字段，单改高度会生成不一致的几何配置；尚未执行下游消费者，不能断言一定崩溃、越界或产出特定错误图像。
